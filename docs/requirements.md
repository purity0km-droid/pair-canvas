# pair-canvas 改修 要件定義

作成日: 2026-09-03
対象: pair-canvas（React + Vite製、キャラクター関係性シート作成ツール）

## 0. 前提条件

- 身内向けに公開しているツール。収益化の予定なし、追加費用（有料ライブラリ・サービス）は避ける。
- 利用ターゲットは女性。PC・スマートフォン両方での利用を想定。
- 説明欄などの自由記述箇所は、既存の使い方（何をどう書くか）のニュアンスを崩さない。
- 動作はなるべく軽量に保つ（重いライブラリの追加は慎重に検討する）。
- 今回の改修では「使用感（見た目・操作感）を大きく変えない」ことを最優先とする。

## 1. フェーズ1：内部整理（スマート化）

**方針**：外から見た挙動は変えず、内部のコードだけ整理する。改修後は日本語コメントで「なぜこの実装なのか」「変更したい時はどこを触ればよいか」を残し、非エンジニアの元実装者でも追えるようにする。

### 1-1. Preview / ExportPreview の重複を共通化

- 現状：画面表示用の `Preview.jsx` と PNG書き出し用の `ExportPreview.jsx` に、関係性の件数（1〜4件）に応じたレイアウト分岐がほぼ丸ごと重複している。
- 実際にコミット履歴上も「1枚保存用レイアウト調整」「保存時カードレイアウト調整」のように、片方だけ直して差分が出た形跡がある。
- 対応：レイアウト分岐部分を共通コンポーネント（例：`RelationCardGrid`）に切り出し、`Preview`/`ExportPreview` はそこに `ref` と表示先の違い（画面用／書き出し用のクラス名）だけを渡す形にする。
- 変更ヒントとして残すコメント：「カードの並び（1〜4件時のレイアウト）を変えたい場合は、このファイルだけ直せば画面表示・PNG書き出しの両方に反映されます」

**追加要望：入力している時点から、完成イメージ（書き出し画像）そのままの見た目にしたい**

実際の出力サンプル（黒背景に白いカード、画像＋名前タグ＋中央の関係性ラベル＋プロット名の黒帯＋説明文、という構成）を確認済み。カード自体のデザインは既に十分魅力的なので、そこを大きく作り変える必要はない。ポイントは、**入力作業をしている最中の画面（Preview）から、この完成イメージがそのまま見えている状態にする**こと。

- 現状、`card.css`/`preview.css` にはスマホ幅（768px/600px以下）専用のレイアウト崩し（キャラクター画像を縦積みにする、カードを1列にする等）が `.paper:not(.export-pc)` という形で入っており、これは画面プレビューにだけ効いて、書き出し（`.export-pc` が付く）には効かない。つまりスマホで入力中に見えている配置と、実際に出来上がるPNGの配置が一致していない。
- 対応：入力中のプレビューも常に書き出しと同じ固定レイアウトで表示する。画面が狭い場合はレイアウトを組み替えるのではなく、`transform: scale()` でカード全体を縮小表示する。追加ライブラリ不要、CSS1行で実現できる（Canva等の編集画面と同じ考え方）。
  - これにより「入力している時点で、すでに完成イメージそのものが見えている」状態になる。文字が小さく見える場合はピンチズームやスクロールで確認する運用になる。
  - 上記のスマホ専用レイアウト崩しのCSS（`:not(.export-pc)` 系のルール一式）は、この変更に伴って不要になるため削除する。

**懸念点への回答：説明欄が長いと画像が潰れないか**

- 説明欄などの自由記述には文字数制限を設けない方針（前提条件どおり）だが、`transform: scale()` は**カードの横幅を画面幅に合わせて縮小するだけ**で、文章の長さで縮小率が変わる設計にはしない。画像（`imageBox`）はカード内で常に決まったサイズなので、説明文がどれだけ長くなっても画像の見え方（縮小率）自体は変わらない。文章が長い分だけカード全体の縦が伸び、その分プレビュー内のスクロール量が増える、という挙動になる。
- ただし、極端に長い説明文が入るとカードの縦がかなり長くなり、プレビュー内スクロールが大変になる可能性はある。その場合の追加対策として、説明欄の表示自体に**上限の高さ＋その中でスクロール**（文字数を制限するのではなく、表示エリアだけ区切る）を持たせる案もある。これは今回必須ではないが、実装時に長文で試してみて、必要であれば追加する。

### 1-2. 関係性データの初期値を1箇所にまとめる

- 現状：関係性オブジェクトの初期形（id・名前・画像・説明など）が、初期state と `addRelation` 内の2箇所に別々に書かれている。
- 対応：`createRelation()` のような関数を1つ用意し、両方から呼び出す形にする。
- 変更ヒント：「関係性データに新しい項目を追加したい場合は、この関数と、保存/読込処理（JSON周り）を確認してください」

### 1-3. 未使用コードの削除

- `RelationEditor.jsx`：現状どこからも読み込まれていない未使用コンポーネント。削除を提案します（将来使う予定があれば教えてください、その場合は残します）。
- `ExportPreview` に渡されている `exportMode` という値：受け取り側で使われていません。用途が無ければ削除、意図があれば実装を追加します。

### 1-4. Lintエラー・警告の解消

- `PageSettings.jsx`：使われていない `fileInputRef` を受け取っている（ESLintエラー）。
- `ImageUploader.jsx`：不要な `eslint-disable` コメントが1件残っている。

### 1-5. 壊れにくさの補強

- `loadProject`（JSON読込）は現状パース成功・失敗しか見ておらず、形式が想定と違うJSONを読み込むと後続の表示でエラーになる可能性がある。最低限の形チェックを追加する。
- 関係性の上限「4件まで」が `App.jsx` と `RelationPanel.jsx` の2箇所に数字（マジックナンバー）としてそのまま書かれている。定数化し、「上限を増やしたい場合はここを変更」というコメントを添える。

### 1-6. PNG書き出しの安定化・ローディング表示

現状の `savePng` は「同じ要素を2回レンダリングする」ことでSafari／iPhoneでの書き出し崩れに対処しているが、これは根本原因（フォント・画像の読み込みタイミング）への対症療法で、待ち時間（固定100ms）も当てずっぽう。調べた範囲では以下のような改善余地がある。

- **原因の切り分け**：`html-to-image`（内部的に用いているsvg `foreignObject`方式）は、①スタイルシート・フォントがCSSOMに登録される前にキャプチャすると文字化けやフォント欠けが起きる、②Safari（特にiOS）は画像のデコードタイミングがフレーキーで、初回キャプチャで画像が消えることがある、という2種類の既知の問題がある（[html-to-image #211](https://github.com/bubkoo/html-to-image/issues/211)、[dom-to-image #343](https://github.com/tsayen/dom-to-image/issues/343)）。今の「2回レンダリング＋100ms待ち」は、この両方を運任せで回避している状態。
- **対応案**：固定待ちではなく、`document.fonts.ready` を待ってから1回目のキャプチャを行い、対象画像（`<img>`）がすべて `complete`（デコード済み）になっているのを確認してから本番キャプチャする。これにより、待ち時間を条件に応じて可変にでき、成功率も上げやすい。ただし、Safariの `foreignObject` 実装自体が本質的に不安定（[html-to-image #348](https://github.com/bubkoo/html-to-image/issues/348)）なため、「保険としてのリトライ」自体はゼロにはできない。2回レンダリングという構造は残しつつ、待ち条件だけ賢くする形を提案する。
- **軽量化のおまけ**：フォントの埋め込みCSSを毎回自動計算させず、`getFontEmbedCSS` で1回だけ取得して使い回すと、書き出し処理そのものが速くなる（ライブラリ側が提供しているオプション）。
- **ローディング表示**：書き出し処理中（PNG生成〜ダウンロードまで）は数百ms〜1秒程度かかるため、その間ボタンを無効化し、簡単なスピナー等を表示する。実装は既にasync関数なので、`try/finally` で表示状態を管理するだけで対応できる。

なお、`ImageUploader.jsx` 側にある「画像選択イベントがSafariで発火しない問題」への対策（`display:none`ではなく透明化＋ネイティブ`addEventListener`で拾う実装）は、iOS Safariの既知の不具合に対する定番の回避策と一致しており、現状の実装で概ね妥当。今回はここには手を入れず、「なぜこの書き方をしているか」が分かるようコメントを補強するに留める。

## 2. フェーズ2：画像の位置・拡大縮小調整機能

### 目的

現状は画像を枠にそのまま自動フィットさせるだけなので、見せたい部分を選べない。ドラッグでの位置調整・拡大縮小ができるようにする。

### 想定操作

- PC：ドラッグで位置調整、スライダー（またはホイール操作）で拡大縮小。
- スマホ：タッチドラッグで位置調整、スライダーで拡大縮小。
  - ピンチ操作（2本指での拡大縮小）は実装コストが高いため、第一段階では見送り、スライダーでの調整を基本とします。必要であれば後日ピンチ対応を追加候補として検討できます。

### データ構造の変更（案）

関係性オブジェクトに、画像ごとの変形情報を追加します。

```json
{
  "leftImage": "data:image/...",
  "leftImageTransform": { "scale": 1, "x": 0, "y": 0 },
  "rightImage": "data:image/...",
  "rightImageTransform": { "scale": 1, "x": 0, "y": 0 }
}
```

この情報は、JSON保存/読込・PNG書き出し（ExportPreview）の両方に反映させる必要がある。

### 実装方針

- 追加ライブラリは使わず、CSSの `transform: translate() scale()` と素のPointer Events（マウス・タッチ両対応）で実装可能。「費用をかけない・軽量」という前提に合う。
- 「位置・倍率をリセット」ボタンを用意する。

### 影響範囲

`ImageUploader.jsx`（操作UI）／`RelationCard.jsx`（表示側での反映）／`App.jsx`（データ構造・保存/読込）

## 3. 中央ラベル（⇄）まわりの自由入力化

### 目的

現在、矢印「⇄」の上に「関係性」欄（自由記述）が1つだけ表示される仕様。矢印の**上と下、両方に自由入力欄**を置けるようにしたい。文章だけでなく、絵文字だけを置くような使い方（例：🌙、💢 など）にも対応する。

### 仕様（案）

- 関係性オブジェクトに、矢印の下用の新しい項目を追加する（例：`relationSub`）。既存の `relation` 欄はそのまま「上のラベル」として使う（データ移行不要）。
- 入力欄は既存の「関係性」欄と同じ、ただの自由記述（テキストエリア）でよい。絵文字も含めて何を入力するかはユーザーに委ねる。専用の絵文字ピッカーなどは今回は用意しない（費用・軽量方針のため）。
- 表示は「上ラベル → 矢印 → 下ラベル」の順で1つのまとまり（暗色スクリムのチップ）として重ねる。元実装の「ラベルが矢印の上」という並びはそのまま維持し、下に1段追加する形。
- 下のラベルが未入力の場合は、その行を表示しない（矢印だけのシンプルな見た目に戻る）。

### 影響範囲

`RelationAccordion.jsx`（入力欄の追加）／`RelationCard.jsx`（表示側）／`App.jsx`（データ構造・保存/読込）

## 4. 追加機能（採用）

提案した候補のうち、以下の2つを実施することが決まりました。

1. **自動下書き保存**（localStorage）：誤ってリロード／タブを閉じた際の作業消失を防ぐ。追加ライブラリ不要、実装コスト低。
2. **フォント選択のプレビュー化**：フォント選択の選択肢が現状テキストのみで見た目が分からない。各選択肢に実際のフォントを当てて見た目を確認できるようにする。

それ以外の候補（削除確認ダイアログ／書き出しサイズプリセット／文字数目安表示／ダークモード）は今回は見送り。

## 5. 進め方（提案）

1. フェーズ1（内部整理）から着手。1コンポーネントずつ、動作を目視確認しながら進める。
2. フェーズ1完了後、フェーズ2（画像位置・拡大縮小機能）、3章（中央ラベルの自由入力化）に着手。データ構造の変更が絡む部分なのでまとめて進める。
3. 4章の追加機能（自動下書き保存／フォント選択プレビュー）は、既存コードへの影響範囲が小さいため、フェーズ1の内部整理と合わせて着手して問題なければ先に組み込む。

品質担保について：現状テストコードが無く、新規導入は今回の「軽量・低コスト」方針とは相性が良くないため見送ります。ビルド（`npm run build`）・Lint（`npm run lint`）が通ることの確認と、目視での動作確認を基本の品質チェックとします。

## 6. デザイン・機能要件の再整理（参考ツールを踏まえて）

フェーズ2「デザイン調整」の方針を、以下の内容で差し替え・拡張する。実装前にこの章の内容についてフィードバックをもらってから着手する。

### 6-0. 目的の再確認

- 本ツールの主目的は、**ユーザーがzetaで実際に遊んでいるシナリオの「キャラクター間の関係性」を可視化・共有するための紹介画像を作ること**。
- zeta自体の宣伝・プロモーションが目的ではない。zetaのロゴ・公式ビジュアルの流用や、「zeta公式であるかのような誤認」を招く表現は避ける。

### 6-1. 参考にしたツールと、著作権・オリジナリティへの配慮方針

ユーザーから提示された2つの参考サイトを確認した。

- **ZETA自プロ紹介画像メーカー**（aki-maron.site/jipuro/）：「自プロ（自作シナリオ）」の紹介カードを作るツール。レイアウトプリセット（SPLIT／POSTER／EDITORIAL／MINIMAL／PORTRAIT／STORYBOOK／BOLD FRAME／PAPER CUT／CINEMA／VERTICALの10種）と、カラーテーマプリセット（ROMANCE／DARK／FANTASY／MIDNIGHT GOLD等）が特徴。白背景・余白多め・ボーダーレスなカードUIで、プリセットは色つきの丸みを帯びたチップとして選ぶ形。
- **推しキャラ語りメーカー**（oshinote.netlify.app）：好きなキャラクターについて語るための単一キャラクター紹介画像ツール。単色（紫）のシンプルなUI。

両方とも同じzetaファンコミュニティ向けの画像生成ツールであり、本ツールの利用者層と重なる可能性が高い。そのため「良いUXパターンは参考にしつつ、固有の表現は明確に距離を取る」方針とする。

**取り入れるもの（一般的なUI/UXパターン・考え方のレベル）**

- 「シームレス」な質感：白い箱＋罫線で仕切るのではなく、余白と丸み・柔らかい配色で区切る構成（フェーズ2で着手済みの方向性と一致するため継続）。
- 「レイアウトプリセット」という機能コンセプト自体（複数の完成形テンプレートからワンタップで切り替えられる）。
- プリセットを色つきの丸いチップ／カードで視覚的に選ばせる、というUI手法。

**明確に避けるもの（固有の表現・具体的な意匠）**

- プリセット名・カラーテーマ名をそのまま流用しない（「SPLIT」「POSTER」「ROMANCE」「MIDNIGHT GOLD」等の具体的なネーミングや組み合わせ・並び順）。
- 参考ツール固有のフィールド構成（自プロタイトル／ジャンル／公開状況／推しポイント／QRコード等）を持ち込まない。本ツールの主役はあくまで「2人のキャラクターの関係性」であり、そもそも内容モデルが異なる。
- 配色の具体的なグラデーション配合や、特定のビジュアルモチーフ（星の散らし方・フォント選定など）を画素レベルで模倣しない。
- ロゴ・サービス名・キャッチコピーなど、識別性の高い文言は流用しない。

**方針**：デザインの「考え方」だけを抽出し、プリセット名・配色・レイアウトの中身は本ツール独自に新規で作る。

### 6-2. フィードバックを受けての方針確定

ユーザーからのフィードバック：

> 使いやすさ自体は後者（推しキャラ語りメーカー）のサンプルが勝っている。機能・操作性の面では後者、シームレスデザインとしてのUIデザインは前者（ZETA自プロ紹介画像メーカー）、という感じ。

これを受けて方針を以下のように確定する。

- **UIの見た目（質感）**：前者（aki-maron）寄りの「シームレス」路線を継続。フェーズ2で先行実装済みの「単色紫＋ボーダーレス＋フレームレス画像」の方向性はそのまま維持する。
- **機能・操作性**：後者（oshinote）寄りの、シンプルで迷わない操作感を優先する。前者のような「レイアウトプリセットをチップ形式で前面に並べる」構成は、本ツールの主画面には持ち込まない。
- **レイアウトプリセット的な機能の位置づけ**：メイン機能ではなく**「おまけ」機能**として扱う。既定では折りたたんだ状態（`▼` を押すと開く詳細設定）にしておき、普段の操作フローには出てこないようにする。

### 6-3. 「おまけ」機能：写真のサイズ比率調整

6-2の方針に沿った最初の「おまけ」機能として、関係性ごとに**左右の写真の大きさの比率**を変えられるようにする。

- 各関係性のアコーディオン内に、`▼ レイアウト（おまけ）` のような折りたたみ項目を追加し、既定では閉じておく。
- 開くと、写真の大きさ比率を選べる（たたき台）：**均等（既定）／左を大きく／右を大きく**の3択。
- 見た目の実装は、現状の各サイズ（large/medium/small）の画像枠サイズを基準に、大きい方・小さい方をそれぞれ一定倍率（例：1.2倍／0.8倍）で拡大縮小する形にする。縦横比は変えない（位置調整モーダルのクロップ枠の縦横比計算に影響を与えないため）。
- あくまで「配置の主従関係」を変える軽い調整機能であり、フェーズ2で検討していたような複数レイアウトのプリセット切り替え（スタック／ミニマル等）は、必要になった時点で改めて検討する。

### 6-4. 進め方

- 6-3の「写真のサイズ比率調整」から着手する。フェーズ1（基本要件）の追加機能として実装する。
- UIの見た目のシームレス化（フェーズ2）は、既存の方向性のまま別途進める。
